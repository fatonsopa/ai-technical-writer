## Document-specific acceptance

These are this package's adopted conventions, not a claim that every organization mandates identical headings.

| Reference | What its template and completed example must demonstrate |
| --- | --- |
| product_requirements_document (PRD) | Product problem/opportunity, target users and needs, goals, scope/non-goals, prioritized capabilities, known success criteria, assumptions/open decisions, and links to the behavioral specification. No invented metrics or implementation design. |
| issue (Issue / Work Item; WI) | Description, scope or limits, specification source for change work, verifiable completion, and type-appropriate additions. Route to user_story.md and relevant testing guidance when those formats are requested; keep their structures in their owning references. |
| user_story (US) | A coherent user need with actor, capability, value, and observable acceptance criteria, linked to relevant requirements and preserving unknowns. Demonstrate a complete story within a Feature/Improvement work item or PRD/SDD; do not require a standalone story file or force one sentence formula. |
| bug_report | Environment, reproduction or known observation sequence, expected and actual results, impact, evidence, relevant files, and verification. |
| decision_record (DR) | A title describing the situation before the decision, context, options considered, a recommended option with reasons and tradeoffs, and the actual outcome only when decided. Suitable for a task-management comment within any task type. |
| policy | Purpose, scope, definitions, principles, policy obligations, responsibilities, compliance, exceptions, and ownership/review. |
| technical_standard | Purpose, scope, definitions, principles, precise rules, verification, exceptions, ownership/review, and related policy or authority. |
| spec_driven_development (SDD) | Status/source, problem and scope, definitions, users and scenarios, identified behavior and business rules, measurable quality constraints, interface behavior, acceptance mapping, and open decisions. Include focused guidance and a complete example for individual requirement entries with ID, source, condition, obligation, exceptions, verification, and status. The filename is the user's convention; the document remains a behavioral specification. |
| high_level_document (HLD; also High Level Design) | Scope/status, requirements and definitions, system context, major components/integrations, runtime/data flow, operations, linked architectural decisions, and risks. Current architecture is verified; proposed architecture is labeled. |
| low_level_design (LLD) | Component scope, linked requirements/HLD, internal responsibilities and interfaces, data structures and algorithms where needed, state/error behavior, design tradeoffs, and verification implications. Detail fits the actual component; it does not repeat the implementation schedule. |
| architecture_decision_record (ADR) | Shared decision structure applied to an architectural choice, with architectural drivers, meaningful alternatives, recommendation and consequences, requirement/HLD links, confirmed status/outcome, and supersession where applicable. |
| design_decision_record (DDR) | Shared decision structure applied to a significant component/internal design choice, with constraints, alternatives, recommendation and tradeoffs, LLD/requirement links, confirmed status/outcome, and supersession where applicable. |
| implementation_plan (IP; plan) | Problem/goal, specification and definitions, current context, approach, ordered steps and dependencies, requirement-to-test coverage, rollout/recovery, and risks/open decisions. |
| test_plan (TP) | Test basis, objectives, scope/exclusions, risks, approach, responsibilities/resources where known, environment/data needs, entry/exit criteria, and planned reporting. Fits a section in the implementation plan or a justified separate testing effort. |
| test_specification (TS) | Requirement/coverage links and repeatable test cases with objective, preconditions, inputs, expected results, and procedures/setup/cleanup where needed. Separate intended outcomes from observed execution evidence; include models only where useful. |
| test_status_report (TSR) | Reporting period and build/environment scope, progress and evidence to date, results/coverage, blockers, changed risks, and next steps. Accurately represents an ongoing effort and supports a concise task comment. |
| test_completion_report (TCR; test summary report) | Scope/build/environment, testing actually performed, results and coverage, departures from the plan, unresolved defects, residual risks, completion assessment, and evidence links. Preserves unknowns, unrun checks, and the distinction between recommendations and approval. |
| tutorial | Learning goal, starting environment, a complete exercise with observed results, completion check, and what was learned. |
| how_to_guide | Task goal, prerequisites, exact actions, expected observations, success check, and applicable failure/recovery branches. |
| explanation | Central question, context, causal relationships, example, tradeoffs, and limits. |
| readme | Purpose, prerequisites, a working start, checks, useful project structure/help links, and spec location when applicable. |
| incident_report | Status, impact, sourced timeline, response/recovery, causes and unknowns, lessons, and owned verifiable follow-up work. |
| agents_and_skills | Correct separation of agents, reusable skills, and output styles; minimal checked formats; task/authority boundaries; an example of each. |
| visuals | Purpose and scope of a visual, labels/connections, a textual explanation, accessibility, and consistency with the specification and prose. |
| writing_style | Existing accepted language principles, Google's tone guidance, six source-backed Linear pairs, preservation, and a meaningful prose review. |

A reference about a document has writing principles even when the resulting document does not need a Principles heading. Definitions and Principles are explicit in both governance document types. Other types include definitions where needed to interpret the specification; do not fill documents with empty boilerplate.

Update routing, checks, and all renamed paths. Keep rewrite safeguards and an optional maintenance workflow.

Maintain compact, complete templates and examples whose facts agree with their stated scenario. The specification owns intended behavior; design documents explain the approach; plans and issues describe work; validation provides evidence. Describing existing code does not silently redefine intended behavior. If a project has no approved specification, draft one or identify the missing decisions before claiming implementation readiness.

Use the document relationships that fit the work. An issue can trigger a specification and plan; a specification and plan can instead produce several implementation issues. User stories describe user value within a Feature/Improvement work item or PRD/SDD and connect to acceptance criteria; they do not add a task type or mandatory stage. The SDD document retains detailed expected behavior, while the implementation plan defines delivery. Consult the existing architecture when planning changes and propose the necessary architecture for a new system. A small issue with explicit expected behavior and acceptance criteria can be the specification source; a separate file is not mandatory. A plan cannot silently redefine the specification. Record conflicts and resolve the affected requirement before marking work ready. Architecture updates after implementation describe verified changes, while proposed views remain labeled as proposals. Do not enforce a universal issue-first sequence.

Test small embedded testing content as well as larger standalone documents; logs are fixtures, not required generated documents.

Reconcile existing evals and writing-style cases; retain provenance. Use task-specific properties rather than exact prose matches, and test graders against known good and faulty samples. Separate development/regression cases from held-out acceptance data and keep generator inputs free of expected answers. Calibrate model judgments against independent human labels when available; disclose when labels or review are only the author's.
