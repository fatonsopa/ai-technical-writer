Approved scope from revision 21, carried into this native change. The owner approved the change at the [behavioral specification](specs/spec-driven-authoring/spec.md). ## Context

The handoff spans checked document authoring, a pinned OpenSpec CLI and two coding hosts. The supported entry today is Technical Writer. The target release has one SpecDev entry backed by the native workflow. [Change proposal](proposal.md)

<a id="goal-and-specification"></a>

## Goals / Non-Goals

**Goals.**

One SpecDev entry writes project documents and uses the installed OpenSpec release for all overlapping work. The user can ask in ordinary language or select a document. Preserve existing documents, approvals, exact literals, checked writing and the working `technical-writer` entry. Ship the target name `specdev` after Builder B5/T50 accepts it. Keep the existing repository and clone URL.

**Non-goals.** The live rename follows the accepted Builder dependency. A planning request cannot authorize implementation, publication or archive; the three parked stories remain outside the execution queue.

## Decisions

The current skill's [integration rule](../../../SKILL.md#document-relationships) and [Task guide](../../../references/task.md) can produce a competing template or require a Task for every row. W40, W47 and W58 change the actual authoring, checking and consuming paths together. The [seven authoring cases](specs/spec-driven-authoring/spec.md#seven-authoring-cases-and-hierarchy-acceptance) prove capabilities available on request. They are not a document checklist for every change.

Use the smallest record a reader can act on. A bounded repair can finish in the existing Task. An OpenSpec feature uses the artifacts the active schema requests. A short task includes its check in the native row. Link a separate Task, design, contract or runbook when it has independent ownership, a reader or a decision to support. For this change, the native task rows link to the already authorized Tasks. OpenSpec reads their checks and states from that single task list.

## Reuse the upstream implementation

**W47 owns installation and routing.** Consume the supplied [private npm manifest](../../../tools/openspec/package.json) and [lockfile](../../../tools/openspec/package-lock.json). In the installed SpecDev tools directory run `npm ci` with a compatible Node.js version (at least 22.20.0). Resolve the local executable from that installation and use the matching released skills where the native workflow uses agent instructions. Reuse the same dependency across projects for that installation. The chosen version is `@fission-ai/openspec@2.1.1`. Its CLI and shipped skills belong together. For an explicit `/specdev init` (Codex: `$specdev init`), run this executable’s `init` in the chosen project. On a new local project use `--tools none` for a SpecDev-only setup. Pass through explicitly requested supported options and preserve native behavior for an existing project or store. Read back the resolved root with `openspec list --json`. Starting standalone writing leaves the project untouched. [OpenSpec release](https://github.com/Fission-AI/OpenSpec/releases/tag/v2.1.1) · [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

**Select the owner before writing.** Use the user's requested action, named change or destination, and the native project's resolved root, active schema and installed operations. For a native operation, pass the selected context to released OpenSpec instructions and CLI. Upstream owns artifact paths, templates, prerequisites, project discovery, verification, apply, status, sync and archive wherever it supplies them. Respect native configuration, custom types, optional operations, errors and authority. A missing prerequisite or ambiguous target has to be resolved before a write. One read-only request cannot authorize setup, implementation, sync or archive. A new OpenSpec capability takes precedence wherever it covers a formerly local operation. Resolve commands at invocation from installed CLI help and available workflow metadata. An unknown local command must be looked up upstream before it is rejected. On a match, forward the supported arguments as data under the original authority. On a name collision the native operation wins. An unknown command in both places returns a clear result with no write. W47.1 uses a native verb with no local alias; W47.2 covers the missing case. Use published interfaces instead of a copied command list. [Native skills](https://openspec.dev/docs/skills) · [CLI](https://openspec.dev/docs/cli) · [Project configuration](https://openspec.dev/docs/project-config)

**SpecDev additions.** Preserve source-grounded writing, session language and document types the selected workflow does not own. Use the native design structure as the baseline for specialized standalone design guidance. Edit an existing decision at its source and cite it from other files. Use a template or review only for the operation and scope requested. A human-facing policy review may identify an unsupported permission in native text; a native validation pass and a product test answer different questions.

**Write native prose with the shared guide.** When SpecDev creates or edits an OpenSpec Markdown artifact, resolve the selected artifact through OpenSpec and read [Writing Style (WS)](../../../references/writing_style.md) from the installed skill. Give the author both the native instructions (including project context and artifact rules) and the guide. Use this same path for built-in and custom artifacts. Review the finished wording against the source in place. A reference in project context can tell an agent which guide to read, but the reference alone does not load the guide or prove the writing meets it. This requires no schema fork, copied guide or change to project configuration. [OpenSpec project configuration](https://github.com/Fission-AI/OpenSpec/blob/v2.1.1/docs/customization.md#how-it-works) · [Acceptance case](specs/spec-driven-authoring/spec.md#a33b)

**W53 owns upgrades.** A Dependabot npm version-update PR for `/tools/openspec` updates the exact manifest version and lockfile together. Test the affected integration boundary before accepting the new pin. Refresh matching upstream instructions through the supported update route. Preserve project data, customized settings and unrelated host entries. Restore the previous recorded dependency pair on a failed upgrade; keep valid project work. SpecDev never needs to copy or maintain a fork of OpenSpec to take an ordinary update.

### Install once and connect the chosen hosts

Follow the [installation section](../../../README.md#installation) for the promised public commands. Ship the GitHub release route first. Reuse the existing skill installer, resource inventory and Python dependency lock for host setup. Both channels deliver the same versioned payload. Map host ID `claude` to the current installer’s `claude-code` target and `codex` to its Codex target. The npm package exposes `specdev` on PATH. The GitHub installer selects the supported asset for a requested tag or latest complete release, verifies its checksum before activation, and reports which release and paths it owns. Set up the skill’s required runtime dependencies in an owned location or report the missing prerequisite and exact recovery. An npm global install alone registers no hosts.

W46/W47 provide the renamed host entry and the private, locked OpenSpec runtime. W53 supplies the update and recovery checks. Preserve its pin and the native in-session `init` and `update` semantics. The distribution CLI owns only its own version and host management here. Keep user-wide registration separate from optional project initialization. Document macOS, Linux and WSL as supported when verified. Native Windows, Homebrew and other package managers are outside this delivery. Test local release assets and an `npm pack` tarball in disposable destinations. Actual GitHub release publication, npm namespace verification and registry publication are separate release-owner actions. Write the handoff README for the completed release, with Installation before Quick start. Before publishing the release README, check the published URL or registry version for every install channel it advertises. The GitHub release can ship before npm. The public package name is proposed as `@fatonsopa/specdev`; a missing registry listing does not establish ownership.

## Work sequence

1. Bind the accepted Builder candidate. Start with W01 and W03. Ship each bounded change with its normal entry, reader-facing documentation and the smallest check that proves the criterion. W60’s accepted guide is reusable.
2. Deliver the writing and decision rules at their mapped tasks. W29 publishes the [sequence](specs/spec-driven-authoring/spec.md#production-order). W35–W37 expose one catalog mapping every supported document to its command. Keep occupied host names and verify the qualified fallback. W46 follows Builder B5/T50.
3. Connect one real OpenSpec change through W47, then W40 for task creation and W48 for consumption. W44 supplies exact field and Task constraints. Reuse W40’s refund list to show safe independent work and the filter blocked on its API result. W49/W50 prove authorized execution and recovery. W51/W52 keep editorial assessment and defect work proportionate.
4. After W58, W63 applies the shared guide to native prose. W58/W59 show that a standalone writing request and its reviewed result can be used beside the same feature. W53 checks dependency updates. W17 uses applicable evidence from both actual hosts. The [task list](tasks.md) owns individual prerequisites, scope and criterion verdicts.

### Shared Definition of Done

Use the [Skill Builder modify workflow](https://github.com/fatonsopa/ai-skill-builder/blob/docs/autonomous-implementation/SKILL.md) on the bounded candidate. Validate applicable Writer-owned documents on reviewed bytes. Use OpenSpec's own checks on native artifacts and assess source meaning separately. Retain existing safeguards for changed inputs, receipts and historic approvals. Run affected repository checks. Record the criterion verdict, exact candidate, evidence and authorized integration once in the owning work record. Reuse evidence, including across stories, when it proves the same outcome.

For the integrated handoff, an independent reader must recover WEB-09, its excluded automatic retry, reconciliation requirement and stored-state proof from the actual documents. Verify each shipped route through its intended consumer. A missing host observation remains Not demonstrated. Apply the repository's full-suite gate only once the implementation candidate is complete.

## Rollout and recovery

Preserve old checked documents, review receipts, user-owned files and the `technical-writer` identity. If a changed rule breaks an existing consumer, a checkout changes underneath a task, or an upgrade cannot use the same project safely, stop that affected action. Preserve the original failure, restore the last compatible integration inputs and resume at the first outstanding criterion. Project publication and deployment require separate authority.

<a id="risks-and-open-decisions"></a>

## Risks / Trade-offs

The principal risk is a second set of rules taking precedence over OpenSpec. Prove both directions through the same public entry: a named native change uses upstream files, and an explicitly standalone writing task creates only its requested output. An upstream extension can own a type that otherwise belongs to the local catalog. The installed project's actual instructions decide. A user decision is needed only for a material ambiguity the available sources cannot settle.
