# Spec Writer comparative audit

**Updated scope.** The owner requires all seven source-backed artifacts and project-independent authorship. F5 and F14–F19 own the seven artifact gaps individually. F9 corrects authorship. F10–F13 distinguish vague acceptance wording, a missing child example, session instructions and an unnecessary check. F20 owns the public document sequence. F21 owns the choice of which levels a particular improvement needs. F22 owns evidence and authority for asking or deciding. Each finding has an epic in the implementation plan.

**Adopted direction.** Improve the existing skill in place. Prioritise the transfer of acceptance criteria between documents, then improve how the skill writes for the person making a decision. Technical Writer already has a strong specification, linked engineering examples, discovery rules, and exact-output delivery. Its most consequential weakness is that a downstream document can look complete while changing what the upstream document requires.

**Scope and evidence.** I audited Technical Writer at `4a8e7c92e20404f05e68708c1a3ea26c6961b178` using Skill Builder at `222b356fd5ac7a2df9fd9621e3744db883ecede0`. I inspected the named sources at the linked revisions, traced examples into their consumers, read the relevant validators, checked a historical edit, and ran one controlled mutation against the structural checker. The comparisons concern the inspected artifacts. They do not rank model performance. The extended review also traced Lauren Tan’s practices to five repositories and compared them with Mirai’s governing workflow and overlay rules. The proposed writing behavior applies equally to Codex and Claude Code. [Proposed epics and acceptance criteria](./implementation-plan.md)

**What changed after reading the transcripts.** Six of the original nine recommendations now have a more discriminating check. F2 specifies what an unresolved reference must report. F3 requires a reachable verification path. F4 separates a prototype from an approval. W11 under F2 preserves correlated reports before work is split. F6 checks what source the writer actually used. F8 tests routing without revealing the expected route. The transcript review left F1 and F7 unchanged. F9 below incorporates the owner’s subsequent correction about authorship. The recordings supply design evidence. The fixture corruption and the structural checker’s response remain the direct local evidence for F1 and F2.

Commit `abdfd79` changed the key and references to “User Story (US).” The example then tells the reader to lowercase the key and incorporate it into a domain name. In the naming guidance distinguish a document label, a project term and an opaque value before expanding anything. ### F2 · High · A valid plan can name a nonexistent requirement

finding: The template’s coverage table has a requirement and a check. The completed example already does better by adding the work responsible. Its real `WEB-09` row points to T14–T16 for request limits, atomicity and partial failure. In an external copy I changed only the coverage-row ID to `WEB-999`. ### F3 · High · Even a resolved ID can conceal weaker behavior

finding: Mirai’s `FR-1` allows setting, changing and removing a due date. Ticket `SAMPLE-51` maps back to that requirement, and its first criterion names all three operations. Its action sets a date and then removes it. A system that rejects replacement of an existing date could satisfy those two assertions. The ticket’s separate verification sentence mentions changing the date, so the defect is specifically in the detailed scenario. By contrast, ticket 57 carries both the two-second limit and the 500-open-task condition into the actual browser scenario. Tan’s agent could launch the app and collect traces yet could not locate the feature named by the reporter. This exposes a second gap in a superficially complete verification instruction: it can specify the right expected result without telling the consumer how to reach the behavior. [Parent requirement](https://github.com/jetmirhaxhisefa/mirai/blob/ddd183a3728d3fdd9f776755de47d4d314c8925c/registry/examples/prd.md#L59-L62) · [Ticket 51 scenario](https://github.com/jetmirhaxhisefa/mirai/blob/ddd183a3728d3fdd9f776755de47d4d314c8925c/registry/examples/tickets/SAMPLE-51.md#L26-L41) · [Ticket 57 scenario](https://github.com/jetmirhaxhisefa/mirai/blob/ddd183a3728d3fdd9f776755de47d4d314c8925c/registry/examples/tickets/SAMPLE-57.md#L31-L39) · [Part 1, 09:58–10:52](https://www.youtube.com/watch?v=PaPpyQocMww&t=598s)

recommendation: Teach the reviewer to name one plausible wrong implementation that each material criterion must reject. For a change-in-place, start with an existing value, replace it, and observe the replacement. For a denied write, inspect the stored value and prohibited side effect where required. Use the local `WEB-09` example to teach the same distinction for uncertain writes: the system must reconcile the write before offering a retry. Only the administrator may choose to retry. In the existing work item, give the user-facing term, the supported action that reaches it, and the observation that distinguishes success from its closest false positive. For T16, losing the response to batch two leaves its commit uncertain. Require a fresh read before offering an administrator retry. A request count shows dispatch only. A formal model, if used, supports the property it actually models. ### F4 · Medium · The approval reader gets less help than the implementing reader

finding: The product guide covers users, outcomes, scope and open decisions. Its template opens with the problem and users. It gives little instruction on composing a decision someone can make from the opening alone. Mirai writes the detail first and derives a short approval summary. BMAD makes the same distinction between drafting order and reading order in its research workflow. The useful addition is a reader task with a testable result. A mandatory executive summary in every issue would add noise. Roman Ugarte describes a feature already built while the product decision was still open. A decision summary can imply approval simply by presenting working software as settled scope. [Current product template](https://github.com/fatonsopa/ai-technical-writer/blob/4a8e7c92e20404f05e68708c1a3ea26c6961b178/references/product_requirements_document.md#L21) · [Mirai wording](https://github.com/jetmirhaxhisefa/mirai/blob/ddd183a3728d3fdd9f776755de47d4d314c8925c/registry/skills/mirai-write/SKILL.md) · [BMAD synthesis](https://github.com/bmad-code-org/bmad-method/blob/e435a22574fe55722841086e5566420178b98df3/skills/core-tools/bmad-deep-recon/references/synthesis.md#L4-L14) · [BLUF](https://en.wikipedia.org/wiki/BLUF_%28communication%29) · [Y Combinator, 52:33–53:19](https://www.youtube.com/watch?v=y1-9yeYLJUo&t=3153s)

recommendation: For an actual approval, open with the choice, affected user, material change, exclusions and unresolved decision or tradeoff. Draft this after the supporting detail. Link claims to their source where ambiguity would matter. Keep technical identifiers in the detail unless the decision depends on them. In a representative evaluation, a reader given only the opening should recover all material parts. Check each answer against the detailed baseline. Mirai’s reader implementation checks quotation presence, section and length. A real quotation can still support the wrong answer. Use a working prototype with an unresolved inclusion decision in the approval example. The opening must let the reader identify what the prototype demonstrated, which choice remains open and who owns it. Carry the decision into scope only after the governing record changes. **Order is a dependency, not a filename convention.** Discovery can feed a brief and product definition. A multi-capability product needs its capability boundaries before separate specifications. A plan decomposes known scope into parent outcomes, stories and work. A child story inherits a feature or epic outcome. A child task inherits a story criterion. A self-contained issue with its own authority and proof can stand alone. [Governing sequence and boundary cases](./specification.md#production-order)

## Is the writing style right for development?

**Keep the shared voice. Change what the examples teach readers to do.** Technical Writer already favors plain verbs, familiar terms, explicit responsibility, useful passive voice, conditions before dependent actions, and honest uncertainty. It already allows a tutorial, reference and binding rule to sound different. Replacing that with a universal “sound human” filter would make some specifications worse. A permission, a limit, an exact error or an unknown can change the system even when both versions sound natural. This is an editorial comparison of the rules and worked documents. It is not a reader study or a claim about every generated answer. ### Where session guidance actually lives

At the audited revision Technical Writer has **no file named `session.md`**. Its own shared voice applies to questions, progress and delivery. The entry requires that guide before writing and separately binds the final checked response. The output-style reference and example teach how to author a host-specific style for someone else. The progress evaluation checks naming and evidence limits. The delivery contract renders a file link and review status. These are four distinct functions. Mirai’s own `guides/session.md` teaches the writer how to explain something to an owner who must act, with actual before/after examples. Choose a named **Session replies** section in Technical Writer’s existing Writing Style (WS) guide as the portable home. Cross-reference the how-to guide for steps and the delivery contract for checked text. A separate project document or installed host output style would add no demonstrated benefit.
